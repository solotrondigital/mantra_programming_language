# mantrac_checker — Semantic Analysis, Type Checking & Hardware Interaction

## 1. Package Overview & Purpose

`mantrac_checker` is the semantic analysis and static type-checking engine of the Mantra compiler. It sits between syntactic parsing (`mantrac_parser`) and intermediate representation lowering (`mantrac_ir`) or code generation (`mantrac_codegen`).

### Core Responsibilities:
* **Static Type Enforcement**: Verifies that operations are performed only between type-compatible operands, catching type mismatches at compile time before execution.
* **Symbol Table Construction**: Builds hierarchical scope tables tracking variables, constants, functions, classes, methods, and static members.
* **Access Control & Encapsulation Verification**: Enforces language privacy boundaries (`priv`, `pub`, `protected`) and inheritance contracts (preventing instantiation of abstract classes, validating method signatures).
* **Deterministic Diagnostic Generation**: Produces rich, span-attributed diagnostic reports (`DiagnosticLevel::Error`, `Warning`, `Note`) with specific error codes (e.g., `E0101`, `E0102`).

* [`src/diagnostics.rs`](file:///Users/user/Documents/workspace/Mantra-Development/mantra_programming_language/crates/mantrac_checker/src/diagnostics.rs): Diagnostic reporting infrastructure with source spans.

### Data Structures & Enums:
* `TypeChecker`: Semantic analyzer state holding `symbols: GlobalSymbolTable`, `scopes: ScopeStack`, `diagnostics: Vec<Diagnostic>`, and `current_class: Option<String>`.
* `Symbol`: Named entity storing `name: String`, `kind: SymbolKind`, `type_info: Type`, `is_mutable: bool`, `visibility: Visibility`, and declaration `Span`.
* `SymbolKind`: `Variable`, `Constant`, `Function`, `Class`, `Field`, `Method`, `Parameter`.
* `GlobalSymbolTable`: Global registry mapping names to top-level types, function signatures, and class hierarchies.
* `ScopeStack`: Push-down stack of lexical hash maps (`Vec<HashMap<String, Symbol>>`).
* `Diagnostic`: Error message payload with `level: DiagnosticLevel`, `message: String`, `span: Span`, and `code: &'static str`.

### Functions & Methods:
* `TypeChecker::new() -> Self`: Initializes an empty checker with built-in standard types (`Int`, `Float`, `Bool`, `String`, `Void`, `List`, `Dict`).
* `TypeChecker::check_program(&mut self, program: &Program) -> Result<(), Vec<Diagnostic>>`:
  1. **Pass 1 (Declaration Discovery)**: Collects all class declarations and function signatures to allow mutual recursion and forward references.
  2. **Pass 2 (Inheritance & Member Validation)**: Validates class inheritance graphs for cycles, verifies abstract method implementations, and registers fields.
  3. **Pass 3 (Body Checking)**: Traverses all statement blocks, expressions, and returns, verifying type consistency.
* `TypeChecker::check_expression(&mut self, expr: &Expression) -> Type`: Infer and verify the type of an expression. Ensures operands to arithmetic operators evaluate to numeric types, boolean logic evaluates to `Bool`, and argument types match declared parameters.
* `TypeChecker::enter_scope(&mut self)` / `leave_scope(&mut self)`: Manages lexical depth for block scopes (`{ ... }`, loop bodies, branch blocks).

## 3. Communication with Low-Level Language Binaries

While `mantrac_checker` does not emit binary machine code directly, it defines and enforces the binary ABI constraints for subsequent compilation passes:

1. **Size & Alignment Layout Calculation**:
   - Computes struct sizes and memory padding for class members. Ensures that low-level binaries generated by `mantrac_codegen` and `mantrac_ir` align fields to 4-byte or 8-byte natural boundaries.
2. **Calling Convention Type Invariant Enforcement**:
   - Ensures parameter counts and types strictly adhere to host calling conventions (System V ABI, Microsoft x64, AAPCS64). Passing a 64-bit float (`f64`) into a 64-bit integer (`i64`) slot without explicit conversion is rejected at this stage, preventing register corruption (`XMM` vs. general-purpose register mismatch).
3. **Prevention of Low-Level Memory Faults**:
   - By statically forbidding uninitialized reads, type confusion, and invalid method calls, `mantrac_checker` guarantees that downstream native binaries never execute undefined machine instructions or dereference unmapped virtual memory pointers.

## 4. Hardware Interaction: CPU, ALU, and MU (Memory Unit)

### Central Processing Unit (CPU)
* **Symbol Table Traversal in CPU Cache**:
  - The type checker performs intensive lookup passes through `ScopeStack`. The inner search iterates backwards through active scope frames.
  - The CPU instruction pipeline executes tight loops comparing identifier hashes, maximizing the hit rate of the CPU's branch target buffer (BTB).
* **Recursion Stack Frames**:
  - Semantic analysis of deeply nested expressions (e.g., complex AST trees) maps to physical host CPU call stack frames. Function inlining optimization by rustc flattens frequently called helper functions into linear CPU execution blocks.

### Arithmetic Logic Unit (ALU)
* **Compile-Time Constant Folding**:
  - When the type checker evaluates constant expressions (e.g., `let x = 10 * 1024 * 1024`), the host CPU's ALU calculates the result ahead of time:
    - 64-bit integer multiplication (`IMUL`) folds constants into a single immediate constant (`10485760`), saving runtime CPU cycles.
* **Bitwise Operations in Symbol Hashing**:
  - Every variable lookup computes SipHash / AHash digests using 64-bit ALU operations (`XOR`, `ROL`, `IMUL`), rapidly indexing into scope hash tables.

### Memory Unit (MU) / Memory Management Unit (MMU)
* **Scope Stack Allocation & Deallocation**:
  - Lexical scopes utilize Rust's `Vec<HashMap<String, Symbol>>`. Entering a block pushes a frame; exiting pops the frame.
  - Pop operations drop symbols and reclaim heap chunks immediately, maintaining a compact memory footprint in physical RAM.
* **Cache Line Locality of Symbol Records**:
  - Symbols are allocated in contiguous memory buffers where possible. Sequential symbol scanning traverses adjacent 64-byte L1 Data Cache lines, minimizing cache miss latency during long compilation runs.
